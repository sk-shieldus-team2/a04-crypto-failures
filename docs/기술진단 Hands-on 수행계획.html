02프로젝트 개요

통합 환경

대상은 대학생 / 취준생. 산출물은 재현 가능한 취약 진단 환경과 구축 가이드로, 이후 사내 신규 인력 교육과 진단 역량 강화 자산으로 재활용한다.

제안 배경

많은 기업이 온프레미스와 클라우드를 함께 쓰는 하이브리드 환경으로 전환했고, AI 활용도 확산되고 있다. 그만큼 웹과 인프라를 노린 위협이 늘면서 진단 실무 역량의 중요성도 커지고 있다. 이에 대상 환경을 구축 단계에서부터 다뤄 보며 취약점이 어디서 왜 생기는지 체득할 수 있는 실습 환경을 마련한다.

핵심 목표

멘티가 AI를 활용해 진단 대상 환경을 설계부터 구축까지 직접 수행한다. 웹 서비스와 DB가 상시 구동되는 폐쇄형 내부 훈련 공간(외부 접점 없음)에서, 팀별로 맡은 OWASP 취약점을 웹, 서버, DB 계층에 구현하고 조치해 본다.

03추진 목표 & 산출물

통합된 하나의 최종 목표5팀의 결과물이 모여 재현 가능한 진단/모의해킹 환경으로

5팀이 각자 구축한 OS, 웹/WAS, DB 3계층 환경이 하나의 VPC에 모여 통합 진단/모의해킹 환경이 된다.

① 구축

  • 통합 진단 환경 (공통 기반 + 팀 5개)
  • OS, 웹/WAS, DB 3계층 (팀별 구성)
  • 망분리 + 접근제어 체인(베스천)

② 취약 & 방어

  • OWASP* 취약 웹 서비스 (팀별)
  • 취약본, 조치본 각각
  • 취약점별 대응방안, 조치 전후 비교

③ 검증 & 문서

  • 인프라 진단 스크립트, 교차 모의해킹
  • 전체 아키텍처 구성도
  • 재현 가능한 구축/진단 가이드

* OWASP(Open Worldwide Application Security Project): 웹 보안을 연구하는 국제 비영리 재단으로, 가장 치명적인 웹 보안 위험 10가지를 꼽은 'OWASP Top 10'을 발표한다

04전체 아키텍처

하나로 합쳐지는 통합 환경접근 경로: 사용자 -> Fleet Manager -> 관리자 PC -> 베스천 -> DB

외부 SSH(22) 차단 베스천이 폐쇄망 DB 접근제어 DMZ/폐쇄망 망분리 + IAM 최소권한 구축 완료 후 외부 통신 전면 차단

* DMZ는 인터넷 노출 구간이 아니라, 웹 계층을 분리 배치한 교육용 망분리 명명 (전체 폐쇄형 환경)

* 구축 기간에만 NAT로 인터넷을 열어 패키지와 이미지를 받고, 구축이 끝나면 외부 통신을 모두 끊어 폐쇄형으로 전환 (Fleet Manager 접속은 SSM VPC 엔드포인트로 유지)

05아키텍처 상세

접속과 접근통제외부 접점 없는 폐쇄형 환경, 모든 접속은 SSM으로만

SSM 전용 접속

외부 SSH(22)와 RDP를 열지 않고 AWS Systems Manager(HTTPS 443)로만 진입한다. 셸은 Session Manager, Windows 화면은 Fleet Manager Remote Desktop을 쓴다.

폐쇄형 운영

구축 기간에만 NAT로 인터넷을 열어 패키지와 이미지를 받고, 완료 후 외부 통신을 전면 차단한다. 차단 뒤에도 SSM은 VPC 엔드포인트로 동작한다.

두 접속 관점 분리

관리자 PC(관리 서브넷)는 서버와 DB를 보는 내부 점검자 관점, 공격 인스턴스(공격자 서브넷)는 웹을 보는 외부 관점이다. 두 관점을 서로 다른 서브넷과 인스턴스에 둬서, 어느 쪽으로 접속하느냐에 따라 관점이 갈린다.

보안그룹 + 최소권한

네트워크 도달 범위는 IP 대역이 아니라 역할 보안그룹(SG)으로 정한다. 각 계층은 허용된 역할의 트래픽만 받아, 필요 없는 경로는 처음부터 열리지 않는다. IAM은 접속 계정을 관점별로 나눠, 내부 점검자(관리자 PC)와 외부(공격 인스턴스)에 최소권한 계정을 하나씩 총 2개 둔다.

08팀 내 역할 분담

팀 내 역할 분담한 팀이 자기 환경을 넷이 나눠 짓는다

SEC

접속 / 보안 리더 유력

팀 서브넷 보안그룹과 접근 경로, IAM, 공격 인스턴스, 취약앱의 권한 탈취(접근제어) 파트. 환경 전체를 조망하기 좋은 자리.

OS

OS / 서버

OS 설치와 서버 구성, OS 진단 기준(SRV) 점검. 팀 환경의 토대.

WEB

웹 / WAS

웹 서버와 WAS 구축, 웹 진단(WST), 취약앱의 웹 장악 파트(인증/설정) 구현.

DB

DB / 폐쇄망

DB 구축과 폐쇄망 구성, DB 진단(DBM), 취약앱의 SQLi 및 DB 피벗 파트.

리더

리더는 기술 영역보다 사람 요인(책임감, 소통, 막힌 사람을 먼저 알아채고 이슈를 정리하는 힘)을 우선 — 소통형 인재를 접속/보안 자리에 두는 것을 권장.

09환경 구성 모델

5팀 프로젝트가 하나로 완성

공통 기반 1팀 직접 구축
  • 공용 VPC 및 망분리 (관리/공격자/DMZ/폐쇄망 서브넷)
  • Fleet Manager 접속, 외부 SSH 차단
  • 관리자 PC (운영 + 서버/웹 점검)
  • 베스천 (폐쇄망 DB 접근제어 관문 + DB 점검)
  • IAM 최소권한, 보안그룹 체인 기준
팀 환경 × 5 각 팀 구축
  • OS (Linux / Windows) + 웹/WAS + DB(폐쇄망) 3계층
  • 취약 웹앱 (OWASP 기반, 팀별 맵핑)
  • 공격 인스턴스 (팀/개인별)
  • 팀 서브넷 보안그룹 / 접근 경로 구성
완성

모든 환경은 각 팀이 직접 구축한다. 1팀이 공통 기반(VPC/관리자 PC/베스천/IAM)을, 2~5팀이 취약 웹앱 훈련 환경을 맡고, 멘토는 프로젝트 방향성을 잡아주며 막히는 부분을 답해준다. 멘티에게 AWS 어드민 계정을 지급해 마음껏 실습하게 하고, 5팀 환경이 한 VPC에 모여 하나의 통합 환경으로 완성된다.

12OWASP Top 10:2025

취약앱으로 구현할 것과 뺄 것웹 요청이 닿으면 재현되는 취약점은 공격 과제로, 부재/설계/프로세스 문제는 개념/점검으로

구현 가능 (익스플로잇 과제) — 취약본/조치본 각각 배포

  • A01접근통제 — 권한 상승, IDOR, SSRF
  • A02설정 오류 — 기본 계정, 디렉터리 노출
  • A04암호화 실패 — 평문/약한 해시, 하드코딩
  • A05인젝션 — SQLi, 명령어 주입, XSS
  • A07인증 실패 — 로그인 우회, 세션 고정
  • A10예외 처리 — 상세 에러/스택트레이스 노출

구현 불가능 (공격 과제 제외)

  • A09로깅/알림 실패 — 부재 문제, 공격 대상 아님
  • A06안전하지 않은 설계 — 설계 전반, 구현 애매
  • A03공급망 실패 — 실제 공급망 공격 재현 불가
  • A08무결성 실패 — 역직렬화만 선택적(5팀)

기성 취약앱(DVWA, Juice Shop)도 로깅/설계/공급망은 공격 과제로 다루지 않음

구현 포맷

각 취약점은 취약본과 조치본을 각각 배포 — 공격 성공/실패와 대응방안을 나란히 비교.

라이선스

TmaxSoft 3종은 영업대표를 통해 임시 라이선스를 받고, DB2는 Community Edition(설치 시 자동 적용, 만료 없음)을 쓴다. WebLogic, Oracle, WebSphere는 외부 멘티 교육 허용 여부를 확인한 뒤 확정.

참고

계정, 권한, 로그, 설정 같은 진단 항목은 제품이 달라도 원리가 같아, 제외된 OS(AIX, HP-UX, Solaris)에도 그대로 응용할 수 있다.

01
요금 관리
VM 테스트 -> AWS 올리기

AWS는 켜 둔 만큼 요금이 쌓인다. 설치와 설정은 로컬 VM에서 먼저 검증하고, 확인된 구성만 AWS에 올린다.

02
환경 구성
유료 관리형 서비스 대신 최소 구성

관리형 DB, 로드밸런서 같은 AWS 유료 관리형 서비스에 기대지 않고, 실습에 필요한 서버만 직접 띄워 최소 구성으로 만든다.

03
리전 확인
작업 전 리전은 서울(ap-northeast-2)

콘솔 오른쪽 위 리전을 먼저 확인한다. 다른 리전에 만들면 공용 VPC 밖에 생겨 찾기 어렵고, 요금도 따로 나간다.
